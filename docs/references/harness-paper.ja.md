# 論文読み砕き — 強いエージェントにハーネスはどれだけ必要か

[参考資料一覧](index.ja.md) の1本です。英語論文の内容を、日本語で噛み砕いた学習ノートです。

## 1. 書誌情報

- 題名：How Much of a Harness Does a Strong Agent Need for Autonomous ML Engineering?
- 著者：Kirill Brilliantov、Alejandro Hernández-Cano、Emmanuel Abbé（所属は EPFL と Apple。先頭2名は共同筆頭、Hernández-Cano は Apple インターン中の研究）
- 出典：arXiv:2609.40303 [cs.AI]、2026年9月30日投稿（査読前のプレプリント）
- URL：https://arxiv.org/abs/2609.40303

## 2. 一言でいうと

強いモデルには、凝った足場は要らない、という論文です。

同じモデル・同じ制限時間で比べると、既存の本格的なエージェント基盤は、「ファイルの読み書きとコマンド実行だけを持つ最小構成のコーディングエージェント1セッション」に勝てませんでした。性能を決めていたのは足場の工夫ではなく、モデル本体の力でした。

用語を先に押さえます。**ハーネス（足場）** は、モデルの外側で作業手順・探索・記憶を管理するプログラム全体です。**バックボーン** は土台になる LLM 本体です。**MLE** は機械学習モデルの開発作業そのものを指します。**アブレーション** は、部品を1つずつ付け外しして効果を測る実験手法です。

## 3. 背景：なぜこの問いが立つのか

MLE の自動化では、モデルにコードを書かせ、実行し、検証スコアを頼りに探索するハーネスが主流になってきました。

ハーネスは年々重くなっています。探索木、プログラムの集団、記憶の階層、専門エージェントのチームなどが積み重なってきました。

一方で最近のモデルはツール使用の訓練を受け、ファイル操作と実行環境を直接触れる「コーディングエージェント」として動けます。そこで著者らは問いを立てました。モデル自身が計画・実行・デバッグできる時代に、外側の仕掛けはどこまで意味があるのか、と。

## 4. 実験のやり方

題材は MLE-bench（Kaggle コンペ形式の ML 開発タスク集）です。不具合のあったタスクを修正した30件（fixed30）と比較用29件を使い、別のベンチマーク NatureBench 40件でも確認しています。

比較は2段構えです。まず自作の介入部品（探索木、複数エージェント並行など）を1つずつ付け外しし、次に公開済みの本格ハーネス4本（MLEvolve、AiScientist、Arbor、ScienceFlow）と対決させました。

最小構成の基準エージェントは **Malena** と名付けられています。コーディングエージェント基盤 OpenCode の上で、制限時間いっぱいを1セッションで走り続け、ターンが終わるたびに残り時間を伝えて続けさせます。

Malena の道具は read / write / edit / bash が中心で、ハーネス側の追加は3つだけです。提出物を登録する道具、残り時間とリソースを返す道具、バックグラウンド実行の道具です。

条件は厳密に揃えられています。全手法で同じバックボーン、同じ計算資源（エージェント側は A100 80GB 1枚・CPU 12コア・メモリ144GB）、同じ制限時間（主な比較は24時間、NatureBench は8時間）です。

バックボーンは GLM 5.2 を主軸に、Kimi K3、DeepSeek V4 系、GPT OSS 120B など複数が試されました。小さいモデルとして Gemma 4 31B も含まれています。指標はメダル率（人間のリーダーボード基準でメダル圏に入った割合）とパーセンタイルで、95%信頼区間つきで報告されます。

## 5. 結果

### 5.1 一番効いたのは「環境」だった

チャット形式（コードを文章で出すだけ）と、実行環境を直接触れるコーディングエージェント形式を比べると、後者が劇的に良い結果でした。これは本研究で測られた最大の効果です。

この改善は強いモデルだけでなく、Gemma 4 のような小さいモデルでも見られた、と著者らは述べています。なお、この比較の正確な数値は図（Figure 2）のみの提示です。

### 5.2 探索や並行化を足しても伸びない

探索木の方式（Chain、Greedy、UCB1、Best-of-N）を24時間で比べると、差は統計的に有意ではありませんでした。最大の差でも UCB1 が Best-of-N を 2.71 ポイント上回る程度で、95%信頼区間は 0 を跨ぎます。

逆に、探索をモデル自身に任せる Malena 形式は、どの探索方式よりもメダル率で有意に上でした（対比較の差は +6.6〜+11.9 ポイント）。

複数エージェントの並行化も効きませんでした。基礎構成のメダル率 55.7% に対し、サブエージェントへの委任を追加すると 45.2%、並行実行と連絡手段を追加すると 33.3% まで下がっています（14タスク、24時間）。

### 5.3 公開ハーネスとの対決

GLM 5.2 では Malena のメダル率は 62.5% で、外部ハーネスの最良である AiScientist の 47.1% を大きく上回りました。

MLE-bench の17ペアと NatureBench の6ペアを通じ、Malena が負けた相手はいませんでした。ただし、5.5 節の Gemma 4 31B の例外を除きます。

なお Malena は「自分で選んだ提出」と「最良だった提出」の差（選択ギャップ）が 1.876 ポイントと最小でした。候補を同一セッション内で同じ物差しで比べられるため、と著者らは分析しています。

### 5.4 細かい部品の付け外し

残り時間を返す道具は効きました。これと関連道具を外すと、メダル率は基礎構成の 59.4% から 50.6% に下がります。一方、時刻を知らせる割り込み通知は逆効果でした（48.9%）。

スキル集や外部検索などの追加部品は、いずれも有意な改善を示しませんでした。

コンテキストを 100万トークンから 64k に人為的に絞る実験では、メダル率は 57.5% から 50.0% に下がりました（信頼区間は重なります）。要約のたびに文脈の約76%が捨てられる条件です。

### 5.5 例外：小さいモデルでは足場が勝つ場面がある

Gemma 4 31B では絵が変わります。最小構成の Malena はメダル率 17.8%・パーセンタイル 32.35 で、探索木型の MLEvolve は 22.2%・42.88 でした。

タスク単位の対比較では、パーセンタイルで Malena が −10.53 ポイントと有意に負けています。メダル率の差（−4.4 ポイント）は有意ではありませんでした。

別の比較でも、Gemma 4 31B では「複数回試して最良を選ぶ」方式がパーセンタイルで Malena を有意に上回りました（差 −3.97 ポイント）。著者らは、小さいモデルの 256k という文脈長の制約が、長時間セッションの足枷になった可能性を挙げています。

## 6. この論文の前提と限界

第一の前提は「フロンティア級のバックボーン」です。主要な結論は GLM 5.2 や Kimi K3 のような最強クラスのモデルで得られており、小さいモデルでは一部逆転します（5.5 節）。

第二に、題材は MLE で、1タスクに数時間〜24時間かける長距離の作業です。短いタスクを大量に捌く設定とは条件が違います。

著者ら自身の留保もあります。MLE-bench は公開コンペ由来で、学習データへの混入とタスク準備の不具合が知られています。本研究では4タスクを修正し、混入チェックも実施しています。

統計の力も限られます。24時間条件ではタスクあたり3〜4シードしか回せておらず、信頼区間は広めです。「負けていない」という弱い主張は確かだが、効果の大きさは割り引くべき、と著者らは書いています。

また、比較相手側の調整量に非対称性が残る可能性も明記されています。付録では、外部ハーネス側の不具合修正や設定検証の内容が開示されています。

## 7. Gemma 4 コンペへの活かし方

### 7.1 まず tension（緊張関係）を正しく置く

この論文の見出しは「足場は要らない」ですが、主語はフロンティア級モデルです。我々の土台の Gemma 4 は、はるかに小さいモデルです。

論文自身のデータでも、Gemma 4 31B では探索木型ハーネスが最小構成を一部上回りました（5.5 節）。著者らも考察で「弱いバックボーンは手作りの手順（workflow priors）の恩恵を受ける」と書いています。

他チームの報告（未検証）も同じ方向です。足場の工夫が明確に効いたのは小さい E4B のみ（+5.4 ポイントで 15.4%）で、12B は最小構成の足場で 25.2% でした（学習ガイド 9 節）。

つまり結論は「足場は削るべき」でも「盛るべき」でもありません。**モデルの大きさごとに、揃えた条件で測って決める**。これがこの論文の実践的な読み方です。

### 7.2 削らないもの：環境そのもの

論文でモデルを問わず効いたのは、上乗せの仕掛けではなく「実行環境を直接触れること」でした。

我々の足場でいえば、ファイル操作・パッチ・実行のツール群と、ループ内検証（コンパイル、対象テスト、`git apply --check`）がこれに当たります（設計書 4.2〜4.3 節）。

ここは足場というより環境なので、付け外しの測定対象からは外し、残す前提でよいと考えます。

### 7.3 部品はトグル可能にして、アブレーションで決める

持ち帰るべきは、論文の結論そのものより方法論です。各層を設定で ON/OFF できるようにし、練習タスクで付け外しを測ります。

対象は設計書にある層です。ループ検出、失敗フィードバック付きリトライ、時間に余裕がある場合の best-of-n（設計書 4.5 節）、適応的なタスク予算、プロンプトの Few-shot 例などです。

探索木や複数エージェントのような重い仕掛けは、論文でも我々の設計でも優先度が最低です。測る前に足さない、が安全です。

### 7.4 投資の先はバックボーン

論文が「性能の主因」と結論したのはバックボーンです。考察では、コーディングエージェントとしての事後学習が足場の役割を肩代わりする、という仮説も示されています。

我々の分担では、これは小関の事後学習が主戦場という意味になります。特に我々の JSON ツールプロトコルへの遵守は、学習で直接伸ばせるはずの能力です。

その測定点は、受入ゲート（設計書 5.3 節）の「プロトコル遵守 95%以上」です。足場側の工数を増やす前に、まずチェックポイントの素の力を練習タスクで記録するのが先です。

### 7.5 時間予算は実験変数として扱う

論文では、制限時間を延ばすと性能は単調に伸び、エージェント自身が与えられた予算に合わせて探索と収穫の配分を変えていました。

我々の本番は全体約11.5時間を約120タスクで割る世界で、タスク平均は約345秒、上限は1800秒です（設計書 3.1 節）。上限の置き方自体が結果を動かします。

練習タスクで上限を変えて（例：900秒と1800秒）resolve 率を比べ、「全体予算1時間あたり何件直るか」で判断するのが、本番条件に近い測り方です。

### 7.6 コンテキストの狭さは、我々が一番不利な点

論文の小さいモデルで効いた制約は文脈長でした。我々のサービング文脈は 32k で、論文の Gemma 4 31B（256k）よりさらに狭いです。

AST 概要で地図を作る探索と、古い観測のプルーニング（設計書 2.1、4.2 節）は、飾りではなく生命線です。「足場の上乗せ」と混同せず、環境側の必須部品として扱います。

なお論文では、残り時間をモデルに返す道具は有益で、割り込み通知は有害でした。我々の観測に残り時間をどう含めるかは、候補として A/B で測る価値があります。条件が違うため、断定はしません。

### 7.7 実行チェックリスト

フリーズ（設計書 9 節、11月30日頃）までに、次を回します。

1. 設定を2つ用意する。「最小」＝ループ＋ツール＋ループ内検証のみ（ループ検出・リトライ・best-of-n は OFF）と、「全部入り」＝現行設計どおり。
2. 同じチェックポイント・同じタスク上限で、固定した公開練習セット（設計書 7.1 節）を `scripts/run_local_eval.py` で両方回す。
3. 比較する指標は resolve 率を主とし、無効パッチ率、パースエラー率、タスクあたり平均ステップ／トークン、所要時間の p50／p95 を併記する（設計書 7.2 節の指標そのまま）。
4. 採用予定のモデルサイズごとに分けて比べる。論文の予測では答えがサイズで変わるため、全体で1つの結論にしない。
5. タスク上限（900秒／1800秒）も同じ枠で比べ、全体予算あたりの resolve 件数で見る。
6. 差がノイズ範囲なら、単純な方を採用する。本番はオフラインで、部品が少ないほど故障点が減るためです。
7. 結果の数値を評価レポートに残す。Paper Track の題材としても使えます。

## 8. 注意点

この論文は第三者のプレプリントで、査読前の単一研究です。数値はすべて原典の提示どおりですが、再現確認はしていません。

設定の違いも大きいです。MLE（検証スコアを頼りに数時間かけて ML パイプラインを作る作業）と、我々のオフライン Python バグ修正（1件あたり数分、テストの合否で決まる作業）は別物です。

時間スケールも、文脈長も、ハードウェアも違います。順位や効果量をそのまま持ち込まず、「揃えた条件で部品を付け外しして測る」という方法と、「モデルの強さで答えが変わる」という構造だけを持ち帰るのが安全です。

他チームのスコア報告（E4B、12B）は未検証情報です。我々の方針は、自分たちの練習セットでの測定で決めます。
