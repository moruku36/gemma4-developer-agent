# 学習ガイド — Gemma 4 Developer Agent Competition を一から理解する

本書は、このコンペが何で、何を作り、どう採点され、何を勉強すればいいかを一から整理した学習レポートです。

前提知識は機械学習の授業程度を想定しています。チームの設計や実装の詳細は [architecture.ja.md](architecture.ja.md) にまとめているので、ここではコンペそのものの理解に絞ります。

## 1. はじめに

本書の目的は、初参加者がコンペの全体像をつかみ、どこから手を付けるかを判断できるようにすることです。

読み方は自由ですが、「3. 何を作るのか」と「6. 公式スターターの歩き方」だけでも全体の流れはつかめます。

分からない点や未確認の点は、ごまかさず「未確認」と明記しています（9 節）。

## 2. コンペの概要

主催は Google DeepMind、プラットフォームは Kaggle です。テーマは「自律コーディングエージェント研究の加速」で、オープンな言語モデル Gemma 4 を題材にした開発コンペです。

賞金は総額 $100K で、2 つのトラックに分かれます。

Paper Track は、成果物そのものではなく「どう作ったか」の研究レポートを競う部門です。

## 3. 何を作るのか

課題は、Gemma 4 を事後学習（追加の学習）し、オフライン環境で Python のバグを自力で直すエージェントに仕上げることです。

たとえ話で言うと、Gemma 4 は「コードは書けるけれど、まだ見習い」のプログラマーです。我々がやることは 2 つあります。

1 つ目は**特訓**です。バグのあるコードとその直し方の例を学習させ、バグ修正が上手くなるようにします。これが事後学習にあたります。

2 つ目は**仕事の手順と道具を持たせる**ことです。「ファイルを読む → バグを探す → 直す → テストで確かめる → ダメならやり直す」という手順を自動で回すプログラムを用意します。

本番では、このエージェントがネット接続のない部屋に置かれ、バグ入りのプログラムをまとめて渡されます。制限時間内に何件直せたかで勝負が決まります。

なお Gemma 4 には E2B / E4B / 12B / 26B-A4B / 31B という大きさの異なるバリアントがあります。小さいモデルは速くて軽い代わりに能力は低く、大きいモデルはその逆です。どれを土台にするかも設計の一部になります。

## 4. 本番環境と採点の流れ

本番の実行環境は Kaggle ノートブックで、GPU は L4 を 4 枚使う構成です。実行中はインターネットに接続できません。

オフラインでも動くよう、必要なパッケージ一式は **wheelhouse** という名前でデータセットとして配布されます。モデルやライブラリは、この中から調達するのが前提です。

採点の流れは大きく 2 段階です。第 1 段階（Phase 1）でエージェントがタスクごとに修正パッチを生成し、第 2 段階（Phase 2）でそのパッチを実際のテストにかけて検証します。

ノートブックが最終的に `submission.zip` を作り、それが提出物になります。

スコアは「直せたタスクの割合」です。パッチが適用できなかったり、テストに落ちたりしたタスクは 0 点として数えられます。

## 5. 登場する技術要素

### 事後学習（ポストトレーニング）

公開済みのモデルに追加の学習を行い、特定の仕事の「型」を覚えさせることです。このコンペでは、バグ修正の例を学習させて専用の能力を付けます。

### LoRA アダプタ

モデルの全部を書き換える代わりに、小さな追加パラメータだけを学習する手法です。成果物のファイルが小さく、元のモデルに着脱できるのが特徴です。

公式スターターのコードには LoRA アダプタを探して読み込む仕組みが含まれており、アダプタ形式での提出が想定されていることが分かります。

### vLLM

大規模言語モデルを高速に動かすための推論サーバーです。本番ではノートブックの中で vLLM を起動し、エージェントは API 経由でモデルとやり取りします。

### 足場（scaffold）

モデル単体ではなく、ファイル操作の道具、作業手順のループ、時間や試行回数の管理まで含めた「モデルに仕事をさせる仕組み」全体のことです。我々のリポジトリが主に作っているのは、この足場の部分です。

### 評価ハーネス

モデルや足場を変更するたびに、練習用のタスクで自動採点し、変更が良かったかどうかを数値で比べる仕組みです。いわばエージェント版の CI（継続的インテグレーション）で、改善の手応えを測る土台になります。

## 6. 公式スターターの歩き方

最初の一歩は、公式の Getting Started ノートブックをそのまま 1 回動かすことです。Kaggle スタッフの Ryan Holbrook が作成したもので、動く完成形が一通り入っています。

手順は次のとおりです。

1. コンペのページから Getting Started ノートブックを開き、**Copy & Edit** で自分のコピーを作ります。元のノートブックは読み取り専用で、そのままでは実行できません。
2. 右側の Settings で、Accelerator が **GPU L4 x4** になっていることを確認します。
3. Input に wheelhouse のデータセットと Gemma 4 モデルが付いていることを確認します。コピー時に自動で引き継がれるはずです。
4. **Run All** で全セルを実行します。wheelhouse のインストール、モデルの読み込み、vLLM の起動、Phase 1 と Phase 2 の実行、`submission.zip` の生成までが順に流れます。

中身をいじるのは、まず無改造で最後まで走らせてからがおすすめです。各セルが何をしているかは、走らせた後に追うほうが理解しやすくなります。

つまずきどころとしては、ノートブックのコメント欄で、wheelhouse のインストール時にプラットフォーム不一致のエラーや、モジュールの読み込み不足に当たったという報告が見られます。同じ症状が出たら、コンペの Discussion を確認してください。

また、Colab のような Kaggle 外の環境では、`/kaggle/input` のような Kaggle 前提のパスが無く、そのままでは動かしにくくなります。本番の確認は Kaggle ノートブックで行うのが確実です。

## 7. 我々のチームの進め方

チームは 2 名体制です。moruku36（リーダー）が基盤とエージェントの足場を担当し、小関（Kaggle: eggggplant）が ML とモデリング、つまり事後学習の側を担当します。

分担の境界は「重み（または LoRA アダプタ）の受け渡し」と「設定ファイル」だけに薄く保っています。受け渡しの約束ごとは設計書の 5 節に定義しています。

開発と勉強は手元の環境や Colab も併用しますが、本番環境での確認は Kaggle ノートブックで行う方針です。本番の GPU が L4 なので、練習も L4 で揃えると挙動のズレが少なくなります。

進捗としては、足場（scaffold v0.1）と全体設計が 2026-10-31 に完成しています。チーム招待は送信済みで、承認待ちの状態です（2026-10-31 時点）。

今後の進め方は設計書 9 節のロードマップに沿います。直近の目標は、ベースラインのモデルで一通りの流れを動かし、公開タスクで最初のスコアを記録することです。

## 8. 勉強リソース

一次情報に近いものから挙げます。

- **公式 Getting Started ノートブック**（Kaggle）。読むだけではなく、Copy & Edit して実際に走らせることが一番の勉強になります。
- **コンペの Overview と Discussion**（Kaggle）。ルールの要点は Overview、他の参加者のつまずきや主催側の回答は Discussion に集まります。
- **ai.google.dev の Gemma 公式ドキュメント**。モデルの種類や、QLoRA などファインチューニングの公式ガイドがあります。主に学習側の担当範囲ですが、受け渡しの言葉をそろえるために目を通す価値があります。
- **他チームの実験記事**（Medium など）。実践の感覚やスコアの水準をつかむ参考になります。ただし第三者の報告として読み、公式情報とは区別してください。

## 9. 注意点と未確認事項

ここには、現時点で公式に確認できていない点を正直に並べます。詳細は設計書 10 節に対応しています。

- **提出物の正確な形式は未確認**です。ファイル名や必須フィールドの最終仕様は公式ルールで確認が必要で、我々は現状 `predictions.jsonl` という形式を想定して作っています（設計書 10 節 項目 1）。
- **タスク数は未確認**です。設計では約 120 件と想定して時間配分を組んでいます（設計書 10 節 項目 2）。他チームの報告（未検証）では 104 件とされています。
- **採点環境の細部は未確認**です。vLLM が採点イメージにあらかじめ用意されているか、データセットや出力のサイズ上限がどうなっているかは、リハーサルで確かめる必要があります（設計書 10 節 項目 4）。
- **空のパッチの扱いや部分点の有無は未確認**です（設計書 10 節 項目 5）。
- **他チームの実験結果（未検証）** によると、足場の工夫が明確に効いたのは小さいモデルの E4B だけで（+5.4 ポイントで 15.4%）、12B は最小構成の足場で 25.2% でした。これはスコア水準の目安としてのみ使い、我々の方針は自分たちの測定で決めます。
- 締切はすべて 23:59 UTC です。日本時間では翌朝 08:59 になる点を取り違えないよう注意してください。

## 10. まとめ

このコンペは、「モデルを鍛える力」と「モデルに仕事をさせる仕組みを作る力」の両方を競うものです。我々のチームは、その 2 つを分担して進めています。

初心者の最短ルートは、公式スターターを Kaggle で 1 回走らせ、全体の流れを体でつかむことです。細部の理解は、その後に設計書と公式ドキュメントで補っていけます。
